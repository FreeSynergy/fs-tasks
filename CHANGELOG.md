# Changelog

## 0.0.8 (unreleased until tagged)

### English

- **Work board: workers work through fs-tasks.** New commands (all with `--json`, exit codes 0 ok / 1 error / 2 wrong words / **3 conflict**, no ANSI): `claim <id> --as NAME [--until 2h]`, `release`, `next --as NAME [--project P]` (the first ready task, claimed in one step), `status <id> in-progress|done|failed [--note] [--report] [--cost]`, `note <id> <text>` (500 bytes), `check <id>`, and `add` / `list` with `--project`, `--objective CMD` / `--subjective`, `--as`, `--status`. `failed` is the existing JSCalendar progress `failed` (no change on the wire); the board shows it as a column. The protocol is in `docs/worker-protocol.md` (EN + DE, with a runner wrapper).
- **One store, no server by hand.** Every command starts `fs-tasks serve` (in its own process group) if no server answers; a lock file next to the socket makes many clients at once start one server. The window now keeps its tasks in `objects.db` of the data folder, the file the server uses (an old `app.db` is moved there); the window is a **client** of that one server (`--connect <socket>`; it starts the server if none runs and never opens the data file itself), so workers and the board work on one repository, and closing the window leaves the server running. The board and the day list follow changes of other clients at once (the server's change feed, no polling); the classic frontend does not: it reads its list again only at its next action (limit: it needs a reload function in `fs-components`, which this repository cannot add). Claims are `editIf` (compare and set on the revision) and read again after a lost race.
- **Check commands are code.** `check` runs a task's command only if the task was made on this machine (`origin` local; every import is `imported`) by a trusted actor, and only for allowed programs (`cargo`, `fs-release`, `bash scripts/...`; settings in `check-policy.json`); as an argument list, no shell, time limit, output bounded. Otherwise `check command not run: foreign origin` (exit 1, task unchanged, `done` refused). `done` of an objective task needs the passed check. Titles, notes, reports and commands with obvious secrets (`sk-ant-`, `ghp_`, `-----BEGIN`, `Bearer `) are refused.
- **Renamed: "Face" is now "Frontend".** The menu is **Frontend** (entries Classic, Board, Day list), the help and messages say frontend, the code too (`Frontend`, `Frontends`, `FrontendOptions`, `Plan::frontend`, menu entry ids `frontend-…`). The remembered choice in `settings.json` is kept under the key `frontend`; a file of an older version with the key `face` is read once and rewritten atomically with `frontend` (the old key stays in the file). No other behaviour changed.
- Project = label `project:<name>`; `list --project`, and the board's search field finds it (type `project:name`).
- A check that runs too long is ended with its whole process group (Unix; Windows: only the child, documented limit). `--connect` and all other window options are checked against the dispatch of `fs-tasks` by a test that starts the real program.
- Limits: the window does not reconnect if the server dies (restart the window); `claim`, `assign_actor`, paging by place are not on the wire (not available to the window). The `done` gate is a rule of the command line, not of the core (the board moves cards freely). No sync: the claim is a note for this machine. Tested with the real program and pictures of the window and at the cache level; not with a person at a screen.

### Deutsch

- **Arbeitsbrett: Arbeiter arbeiten über fs-tasks.** Neue Befehle (alle mit `--json`, Exit 0 ok / 1 Fehler / 2 falsche Worte / **3 Konflikt**, kein ANSI): `claim`, `release`, `next` (erste bereite Aufgabe, in einem Schritt geclaimt), `status in-progress|done|failed` mit `--note/--report/--cost`, `note` (500 Byte), `check`, dazu `add`/`list` mit `--project`, `--objective`/`--subjective`, `--as`, `--status`. `failed` ist der vorhandene JSCalendar-Fortschritt `failed` (keine Leitungsänderung); das Board zeigt ihn als Spalte. Das Protokoll steht in `docs/worker-protocol.md` (EN + DE, mit Runner-Wrapper).
- **Ein Speicher, kein Server von Hand.** Jeder Befehl startet `fs-tasks serve`, wenn keiner antwortet; eine Sperrdatei neben dem Socket sorgt dafür, dass viele Clients gleichzeitig nur einen Server starten. Das Fenster hält seine Aufgaben jetzt in `objects.db` im Datenordner, der Datei des Servers (ein altes `app.db` wird dorthin verschoben); das Fenster ist **Client** dieses einen Servers (`--connect <Socket>`; es startet den Server, wenn keiner läuft, und öffnet die Datei nie selbst), Arbeiter und Board arbeiten an einem Bestand, und beim Schließen des Fensters läuft der Server weiter. Board und Tagesliste folgen Änderungen anderer Clients sofort (Änderungsabo des Servers, kein Abfragen im Takt); das klassische Frontend nicht: es liest seine Liste erst bei der nächsten Aktion neu (Grenze: braucht eine Reload-Funktion in `fs-components`). Claims laufen über `editIf` (Vergleichen und Setzen auf der Revision), nach verlorenem Wettlauf wird neu gelesen.
- **Prüfbefehle sind Code.** `check` führt den Befehl einer Aufgabe nur aus, wenn sie auf diesem Rechner angelegt wurde (`origin` local; jeder Import ist `imported`) und von einem vertrauten Akteur stammt, und nur für erlaubte Programme (`cargo`, `fs-release`, `bash scripts/...`; Einstellung `check-policy.json`); als Argumentliste, ohne Shell, mit Zeitlimit und begrenzter Ausgabe. Sonst `check command not run: foreign origin` (Exit 1, Aufgabe unverändert, `done` abgelehnt). `done` einer objektiven Aufgabe braucht den bestandenen Check. Offensichtliche Geheimnisse in Titel, Notiz, Bericht und Befehl werden abgelehnt.
- **Umbenannt: „Gesicht/Face“ heißt jetzt „Frontend“.** Das Menü heißt **Frontend** (Einträge Classic, Board, Day list), Hilfe und Meldungen sagen Frontend, der Code ebenso (`Frontend`, `Frontends`, `FrontendOptions`, `Plan::frontend`, Menü-Ids `frontend-…`). Die gemerkte Wahl in `settings.json` liegt unter dem Schlüssel `frontend`; eine Datei einer älteren Version mit dem Schlüssel `face` wird einmal gelesen und atomar mit `frontend` neu geschrieben (der alte Schlüssel bleibt in der Datei). Sonst ändert sich nichts.
- Projekt = Label `project:<name>`; `list --project`, und das Suchfeld des Boards findet es (`project:name` tippen).
- Ein Prüfbefehl, der zu lange läuft, wird mit seiner ganzen Prozessgruppe beendet (Unix; Windows: nur das Kind, dokumentierte Grenze). Alle Fensteroptionen werden von einem Test mit dem echten Programm gegen den Dispatch von `fs-tasks` abgeglichen.
- Grenzen: das Fenster verbindet sich nicht neu, wenn der Server stirbt (Fenster neu starten); `claim`, `assign_actor`, Seiten nach Ort sind nicht auf der Leitung (dem Fenster nicht verfügbar). Das `done`-Tor ist Regel der Kommandozeile, nicht des Kerns (das Board verschiebt Karten frei). Kein Sync: der Claim ist eine Notiz für diesen Rechner. Getestet mit dem echten Programm und Bildern des Fensters sowie auf Cache-Ebene, nicht mit einer Person am Bildschirm.

## 0.0.7 (released)

### English

- **Fix: `fs-tasks --plan classic …` opens the window**: `--plan`, `--open`, `--list`, `--sample`, `--today` and `--export-sensitive` were not known as window options, so such a call went to the command line (`unknown command`) and the typing test saw no window.
- **Import of a long `DEPENDS-ON` chain is linear again**: the tasks of an import are judged for "who became ready" in one pass over the store, not once for each task a relation names (that was quadratic: 300 tasks 35 s in a debug build, 1500 did not finish). Actor IRI (2048 bytes), actor name (200 bytes) and the end of a claim (24 hours) are bounded. The choice of the face is synced to disk before it replaces the old file, and a relative `$XDG_DATA_HOME` is ignored (XDG rule).
- **The window has three faces**, chosen in the menu **Face**: *Classic* (the first window), *Board* (columns by status, cards, a panel with "Move to") and *Day list* (Today, Upcoming, Anytime, Someday, Logbook, labels). The choice is remembered in `settings.json` in the data folder (`$XDG_DATA_HOME/freesynergy/tasks/`), written atomically; a missing or broken file means the default, **Board**. A failed write is a warning, not a crash.
- `--plan classic|board|next` starts with a face this time only and does not change the memory (`board2` and `next2` still work; the earlier workbench layouts are `board1` and `next1`). `--version` / `-V` is unchanged.
- Built on `fs-components` v0.0.13 (the plan widgets live there), `fs-interfaces` v0.0.19. The typing test starts the classic face (`--plan classic`).
- Core: boards, actors as assignees, execution members, claims (see DESIGN.md). **Comments are not in this program**; they live in the comment topic.
- Not done: moving a card with the mouse; Windows was not run; the faces are tested by events, the router and headless pictures, not by a person's mouse.

### Deutsch

- **Fehlerbehebung: `fs-tasks --plan classic …` öffnet das Fenster**: `--plan`, `--open`, `--list`, `--sample`, `--today` und `--export-sensitive` galten nicht als Fensteroptionen, der Aufruf ging an die Kommandozeile (`unknown command`) und der Tipptest sah kein Fenster.
- **Das Fenster hat drei Gesichter**, gewählt im Menü **Face** („Gesicht“): *Classic* (das erste Fenster), *Board* (Spalten nach Status, Karten, Seitenfeld mit „Move to“) und *Day list* (Tagesliste: Today, Upcoming, Anytime, Someday, Logbook, Labels). Die Wahl wird in `settings.json` im Datenordner (`$XDG_DATA_HOME/freesynergy/tasks/`) gemerkt, atomar geschrieben; fehlt die Datei oder ist sie kaputt, gilt der Standard **Board**. Ein fehlgeschlagenes Schreiben ist eine Warnung, kein Absturz.
- `--plan classic|board|next` startet nur dieses eine Mal mit einem Gesicht und ändert das Gemerkte nicht (`board2` und `next2` gehen weiter; die früheren Workbench-Layouts heißen `board1` und `next1`). `--version` / `-V` bleibt.
- Baut auf `fs-components` v0.0.13 (dort liegen die Plan-Widgets) und `fs-interfaces` v0.0.19. Der Tipptest startet das klassische Gesicht (`--plan classic`).
- Kern: Boards, Akteure als Zuständige, Ausführungsfelder, Claims (siehe DESIGN.md). **Kommentare gehören nicht in dieses Programm**, sie liegen im Kommentar-Thema.
- Nicht erledigt: Karten per Maus ziehen; Windows wurde nicht ausgeführt; die Gesichter sind mit Ereignissen, Router und Bildern ohne Fenster getestet, nicht mit der Maus einer Person.
