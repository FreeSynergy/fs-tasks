# fs-tasks – Design

`fs-tasks` is the tasks program of FreeSynergy and the **owner of the JSCalendar `Task`** (ADR 0050: one standard, one
owning program, one interface). This repo holds the **program core** (`crates/fs-tasks-core`, no GUI), the server (`crates/fs-tasks-server`), the **client** of the server (`crates/fs-tasks-client`, see below) and the **frontend** (`crates/fs-tasks-app`, see below). The contract
(`tasks.capnp`) lives in [`fs-interfaces`](https://github.com/FreeSynergy/fs-interfaces) (ADR 0045); this program is its owner. Other programs, e.g. `fs-calendar`, use tasks **only through the interface** (`TaskItems`, `TaskFeed`) and have
no Task model of their own. Design of the whole program: `fs-documentation/docs/en/programs/apps/tasks/design.md`.

## Interface status

**Interface status: draft, consumers: fs-calendar (1 of 2).** (ADR 0045: the interface is a target. It stays draft until two
independent consumers have tested it, then 1.0, then only version jumps.) The contract is `tasks.capnp` in `fs-interfaces` (marked DRAFT; owner: this program). The Rust form comes first (ADR 0043): the traits
`TaskItems` and `TaskFeed`.

## Frontend (`crates/fs-tasks-app`, provisional)

A list and a view by status of one set of tasks; search; create, edit (title, description, due, priority, status, labels), delete; a card moved by keyboard, by the buttons beside the task, or by a frontend's gesture through `TasksWidget::grab`, `hover`, `drop_held`; iCalendar in and out by path on the command line (`--socket`, `--import`, `--export`, `--export-sensitive`, `--snapshot`, `--size`, `--view list|status`). `--socket <path>` is required and names the socket of a running `fs-tasks-server --socket <path>`: without it the app stops and says so; `--store` is refused and points to `--data` of the server. The app opens no store. It imports no `blinc_*` crate. Its menus (ADR 0056, only real commands, in `surface.rs`): Task: New; View: List, Status; the compact variant has none. The work surface is the workbench `tasks` in `fs-components`, which knows no store and no type of this repo and has no window function: it gives its host a plain context (selected key, view; ADR 0056).

**Over the socket.** `TaskAdapter` drives `Arc<dyn TaskItems>`, which in the binary is `RpcTasks` of `fs-tasks-client`, with a tokio handle from the interface thread; the import and export by path (`transfer`) go through the same client. `main.rs` connects before anything else; a server that is not there is a message in words (`cannot reach the tasks server at <path>`) and exit code 1. **Limits, honestly:** `TaskSource` is synchronous, so every call of the workbench **blocks the interface thread** until the server has answered (a slow or stuck server freezes the window for at most the call deadline of 30 s, then the action fails with an error; there is no "busy" state yet). The app has **no `subscribe`**: a change another program makes is not seen until the next read, and `TaskFeed` is not used over the socket. A server that stops shows as an error on the next action; there is no reconnect (restart the app).

**Provisional decision: the status view is not a board.** The design says boards, columns and `task_link` are proposals with no standard, and that moving a card on a board must not change the task for everyone. **Real boards are open and not built here: no new standard, no `Boards` interface.** This first view is a view over the task's own JSCalendar `progress`, one column per value, and it is called "Status" in the GUI, not board or kanban. So moving a card **is an edit of the task's own status, for everyone**, and the screen says so: always above the columns, also that a status worked out from the participants becomes fixed on a move and cannot go back to that in the GUI, and after each move.

| What a move does | |
|---|---|
| Writes | `progress` (the value the person chose) and `progressUpdated`; the core sets `updated` |
| Keeps | everything else, compared as JSON in `tests/moves.rs`: participants and what they said, `percentComplete`, `freesynergy.net:taskStatus`, relations, `extra`, the original iCalendar |
| To the status the task effectively has | writes nothing, so a status the core only computes (`effective_progress`) stays computed. An edit that leaves the status alone does not write it either |
| A task that repeats, or one occurrence | refused with the reason, in the source and on the card: its status belongs to each occurrence, and there is no per-occurrence edit yet. Its form has no due date and no status; title, description, priority and labels change for all occurrences |
| From an old row | a conflict; nothing is written and what is stored now is shown |

**`Unsupported` in the frontend:** own boards, columns other than the five values of `progress`, order within a column (it follows the list: by due date, a card put elsewhere goes back and this is said), swimlanes, column limits, assigning people, relations, `task_link`, checklists, timeline, comments, attachments, reminders, undo, recurrence and per-occurrence edits. What the form does not show stays on the task and is shown on the sheet where it is simple (participants and related tasks by count, percent, extended status). The picker dialogs for import and export do not exist: paths on the command line.

**Sensitive tasks (ADR 0029).** Marked in list, card, sheet and form; never opened by the workbench; `--export` leaves them out and names them by `uid` alone, `--export-sensitive <uid>` releases one, and a file with a released task is mode 0600. **The core has no check of its own:** `is_marked` walks the task for the member `freesynergy.net:sensitive`, also as a patch path in an override, and for `privacy` other than `public`, and reads `envelope.sensitive`; a mention in a text or a key of an id map (a label called `privacy`) marks nothing. To be replaced by the core's. The core also does not fill `envelope.sensitive` from the vendor property, as `fs-people-core` does, so the store's refusal to keep marked objects unencrypted does not apply to tasks marked that way.

**Other limits.** A write compares the revision and then writes: not atomic, `TaskItems::edit` takes no revision (a compare-and-set is a wish for the core). `rows` reads the whole list each time (all pages of the wire, 100 per page) and cuts a page from it: `TaskItems` has no paging or text search. The server cuts each page from a fresh whole list, so a write between two pages can make one task appear twice or be missed in that one read; the next read is right. There is no sign-in, so "my next tasks" (the compact variant) is every open task. Floating tasks are ordered as if in UTC; there is no `--zone` yet. A due date needs a time: "that day" has no form yet. A keyword switched off is kept and not shown; one with a comma stands in quotes in the form. One unreadable stored task makes the whole list and export fail, plainly: `TaskItems::list` answers all or nothing, and the contract has no other way through the tasks (with Thread 3). Closing the window loses an unsaved edit. Provisional words and sizes are in `words.rs`.

## Client (`crates/fs-tasks-client`)

`RpcTasks` is the Adapter of `TaskItems` in front of the Cap'n Proto client of `tasks.capnp`, so a frontend depends on the trait and never on the core (ADR 0021). `RpcTasks::connect(socket)` (or `connect_with(socket, Timeouts)`) starts the shared `Worker<TasksRemote>` of `fs_interfaces::rpc::client` (feature `rpc`): one thread with a current-thread runtime and a `LocalSet` (a capnp-rpc client is not `Send`); `TasksRemote::open` (`remote.rs`) asks `supportReport` and takes the `Items` capability; calls from any thread queue for that thread and overlap there. **Deadlines:** the handshake waits at most 5 s (`Timeouts::connect`), a call at most 30 s (`Timeouts::call`); the text of a missed one is `tasks server did not answer within <limit>` (a `Fault`, as `Store(Backend(..))`). A write that ran out of time may still have happened: the server finishes what it began. **Guard:** a call that panics, or is cut, answers `tasks client: a call ended without an answer` and the thread lives on (proven in the tests of `fs-interfaces`; nothing in the tasks client can be made to panic from outside, so no test here does it). **Drop** closes the queue and the connection and joins the thread: a call under way is cut (it gets `Disconnected`; a write may be left half done). **Not there:** no `subscribe` and no reconnect (a lost server is an error on every later call; restart the app).

| Method of `TaskItems` | Over the wire |
|---|---|
| `capabilities` | what `supportReport` said at connect: a snapshot, the server is not asked again |
| `get` | `Items.get`; `found = false` is `None`, not an error |
| `get_by_uid` | `Items.getByUid`; `found = false` is `None` |
| `query` | `Items.query` with the filter written by `contract::write_filter`, every page like `list` |
| `list` | `Items.list`, every page until the cursor is empty; an empty page that names a next one is an error, not a short list |
| `create`, `edit`, `delete` | `Items.create`, `edit`, `delete`; the task goes as its JSCalendar JSON text |
| `import_ics`, `export_ics` | `Items.importIcs`, `exportIcs` |

**Unsupported (explicit, by name):** `assign` (`task.assign`), `relate` (`relation.create`) and `label` (`label.assign`) are the trait's defaults; `TaskFeed` (`subscribe`, `task.subscribe`) is not implemented by the client, and `boards` is a placeholder in the contract. The server offers the first four: the client leaves them out because the app calls none of them, not because the contract lacks them. **`capabilities()` is cut to match:** the report of the server is read at connect, and those four ids are reported as not possible ("the server offers it, the client of the tasks program does not yet"); everything else is as the server said. A test fixes it.

**What arrives and what does not.** `TaskEntry` is built from the wire: `id` is the envelope's, `task` is the JSON text parsed as `Task` (unknown and vendor properties stay in `extra`), `envelope` is read with `read_envelope` with every field the contract carries (type, name, `context`, IRI, `attributedTo`, audiences, `sensitive`, `startTime`, `endTime`, `published`, `updated`). **What does not arrive:** the store's microseconds (`published`, `updated`, `startTime`, `endTime` come in **milliseconds**, the wire's resolution, so two writes within a millisecond are told apart by the app's content fingerprint alone) and the index fields and the original iCalendar of an import, which `TaskEntry` does not carry anyway. A reply that cannot be read is a store error saying so.

**Errors, read back from type, status and text** (the wire carries no fields), by `problems.rs`: `tasks/not-found` is `NotFound(id)` (the id is read from the text, else it is the call's), `tasks/conflict` is `Conflict(text)`, `tasks/invalid` is `Invalid(issues)` if the text is the core's `JSCalendar 2.0 violation: /path: message; ...` (a message that has `; ` inside stays whole), `Time` or `ICalendar` by their prefixes, else `Store(Invalid(text))` (the store's own `object store: invalid input: ` is not wrapped twice); the issues are split at `; ` outside double-quoted values, because the core quotes the values it names, but a key of an id map that holds `; /` cannot be told apart and splits; `unsupported` (501) is `Unsupported(capability, reason)`; `too-large` is `TooLarge(n)` for the core's task text (`the task and its name have N bytes`) and for a request (`N bytes, at most M fit`), and a store error with the server's words for an answer that is too large (`the answer has N bytes`) or a text with no number; `invalid-request` is `Store(Invalid(text))`. **Deviations from the core:** a conflict or invalid of the store layer (not the core's own variants) comes back as `Conflict` or `Store(Invalid)` with the server's wording nested; `Json` and every other store error of the server come back as `Store(Backend(text))`; a server that is gone, or a call the server does not know, is `Store(Backend("tasks server: ..."))` or `Unsupported("tasks", ...)`, since the core has no variant for a transport failure. A change of wording on the server breaks the reading back; the table is tested in `problems_table.rs` and the common types over the real socket.

**Done with the shared worker:** a timeout per call and per connect, and the guard against a panic in a job. **Still open, only named:** the quadratic reading of pages (the server cuts each page from a fresh whole list, so a read of N tasks costs about N times N/100 on the server). The shared worker does not change it.

**Tests:** the server runs in the test process on a thread of its own (a real Unix socket, the real store and the real client); no test runs the `fs-tasks-server` binary. The overlap of calls is proven by a provider that answers `list` only when two calls are in it at once.

**Shared with the other clients.** The thread, its queue, the deadlines and the guard are `Worker<R: Remote>`, `Timeouts` and `Fault` of `fs_interfaces::rpc::client` (v0.34.0); the generic readers of a problem (`Failure`, `local_type`, `object_id_in`, `without_store_prefix`, `unsupported_of`) are `rpc::client::problems`. Here stay the capability fetched at connect (`remote.rs`), the table of problem types to `fs_tasks_core::Error` with its `tasks/...` URIs (`problems.rs`), and the reading of `too-large`, which has three texts of this program (`first_number` is not used: it would turn a text with no number, or the answer's, into `TooLarge(0)` or the wrong size).

## Decisions

* **Independent of fs-calendar.** `Task` stands on its own (ADR 0050). What it shares with `Event` lives in `fs-jscalendar`, a plain
  library without data or program, so neither program copies it and neither depends on the other for it.
* **Context `tasks`.** Tasks written by fs-calendar 0.1 have `context=calendar`; they are not found by `TaskRepo`. No data
  existed outside tests, so there is no migration.
* **Assign** adds a participant with role `owner`; assigning the same address twice keeps one participant.
* **Relations** use the `Relation` object of JSCalendar (`relatedTo[uid].relation[key] = true`); keys: `first next child parent`
  (RFC 8984) and `depends-on finishtostart finishtofinish starttostart starttofinish` (RFC 9253). Lead/lag gaps are not modelled.
* **Index times are clamped, not refused:** `0000-01-01T00:00:00` in Auckland is valid JSCalendar, so it stays storable. Its index value is the edge of the range and its envelope keeps the real time (provisional).
* **Task envelope type** is `Task` (AS2 has no task type); content type `application/jscalendar+json`.
* **Wire form of a task**: JSCalendar JSON text plus the envelope; the JSON stays authoritative.

## Tags not to use

* **v0.5.0, v0.5.1.** Both pin `fs-interfaces` v0.22.0, whose `rpc` is superseded (see its `DESIGN.md`). In the server: a `due` of 15 MiB of control characters passes intake, its error escapes to more than a message and ends the connection; a report of an import can do the same, and the report is lost; a title of nearly 16 MiB is accepted, and then `list` answers 413 forever, as the title counts twice. In the core: `:60` is taken in any minute; a time near year 0 or 9999 falls out of every range; a `DURATION` raises a false alarm, while garbage in other properties goes unsaid; a continuation line can end a `VTODO`, and data is lost silently (`fs-jscalendar` before 0.1.3).

## Crates

* `fs-interfaces` (git tag v0.34.0; feature `rpc` in server, client and the app's tests): contract, `Capabilities`, `Unsupported`, `rpc`.
* `fs-tasks-client` (this repo): used by `fs-tasks-app`; `fs-tasks-server` only in the tests of both.
* Frontend only: `fs-components-app`, `fs-components-workbenches` (git `rev`, provisional until a tag exists).

## Open points

* **`DURATION` of a `VTODO`:** the conversion (`calcard`) makes it `duration`, not `estimatedDuration`, so it is kept and checked but does not count for the time span. Provisional, not changed here.

* **Capability ids (provisional, question to the owner):** `tasks.capnp` names ids only for five methods. For the rest this repo uses `task.read`, `task.query`, `task.delete`, `task.import`, `task.export`, `task.subscribe` and the planned board ids (`board.open`, `board.create`, `column.create`, `column.limit`, `card.move`). They should be written into the schema or replaced.
* **`supportReport`:** the contract has it on the root; the wire answer is `Capabilities::write` (fs-interfaces). The capnp-rpc server is still not written.

* Second consumer of the interface (needed for 1.0): e.g. the project suite or the hub.
* Boards (`Boards` placeholder), `task_link`, column limits, time tracking (design.md open questions).
* Per-instance changes of recurring tasks are preserved (`recurrenceOverrides`) but not expanded: there is no task recurrence engine yet.
* `TaskChange` carries only the id; richer payloads (envelope) come with the capnp-rpc server (`common.capnp` `Change`).
